## 2. What's queryable

The DB-backed shape replaces re-running Python scripts for inspection. SQL cookbook:

### 2.1 Latest completed CRI run

```sql
SELECT id, composite_version, start_date, end_date, n_days,
       summary->'oos'->>'as_of'                AS as_of,
       summary->'oos'->'versions'->1->>'auc_dd5'  AS current_auc_dd5,
       summary->'oos'->'versions'->1->>'auc_dd10' AS current_auc_dd10,
       summary->'extras'->>'fired_count'       AS fired_count,
       note
  FROM uw_scan.regime_backtest_runs
 WHERE indicator = 'cri' AND completed_at IS NOT NULL
 ORDER BY created_at DESC
 LIMIT 1;
```

### 2.2 Compare two CRI composite_versions side-by-side

```sql
SELECT
  a.composite_version AS ver_a,
  a.summary->'oos'->'versions'->1->>'auc_dd5'  AS auc_dd5_a,
  a.summary->'oos'->'versions'->1->>'auc_dd10' AS auc_dd10_a,
  b.composite_version AS ver_b,
  b.summary->'oos'->'versions'->1->>'auc_dd5'  AS auc_dd5_b,
  b.summary->'oos'->'versions'->1->>'auc_dd10' AS auc_dd10_b
FROM uw_scan.regime_backtest_runs a
JOIN uw_scan.regime_backtest_runs b
  ON a.indicator='cri' AND b.indicator='cri'
 AND a.composite_version='3'
 AND b.composite_version='4-candidate'
 AND a.completed_at IS NOT NULL
 AND b.completed_at IS NOT NULL
ORDER BY a.created_at DESC, b.created_at DESC
LIMIT 1;
```

### 2.3 Level distribution per calendar year for the latest CRI run

```sql
WITH latest AS (
  SELECT id FROM uw_scan.regime_backtest_runs
   WHERE indicator='cri' AND completed_at IS NOT NULL
   ORDER BY created_at DESC LIMIT 1
)
SELECT date_trunc('year', trade_date)::date AS yr, level, COUNT(*) AS n
  FROM uw_scan.regime_backtest_daily
 WHERE run_id = (SELECT id FROM latest)
 GROUP BY 1, 2
 ORDER BY 1, 2;
```

### 2.4 Named-crash VCG window for any event

```sql
SELECT id, composite_version,
       summary->'extras'->'credit_proxy' AS proxy,
       jsonb_pretty(summary->'extras'->'named_crash_window'->'2008-09-15') AS lehman_window
  FROM uw_scan.regime_backtest_runs
 WHERE indicator='vcg' AND completed_at IS NOT NULL
 ORDER BY created_at DESC
 LIMIT 1;
```

Substitute `'2020-03-16'` (COVID), `'2018-02-05'` (Volmageddon), etc.

### 2.5 VCG interpretation distribution for any run

```sql
SELECT level, COUNT(*) AS n,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS pct
  FROM uw_scan.regime_backtest_daily
 WHERE run_id = (SELECT MAX(id) FROM uw_scan.regime_backtest_runs
                  WHERE indicator='vcg' AND completed_at IS NOT NULL)
 GROUP BY level
 ORDER BY n DESC;
```

### 2.6 CRI named-crash hits across all runs

```sql
SELECT id, composite_version,
       summary->'extras'->'named_crash_hits'->'2008-09-15' AS lehman,
       summary->'extras'->'named_crash_hits'->'2020-03-16' AS covid,
       summary->'extras'->'named_crash_hits'->'2018-02-05' AS volmageddon
  FROM uw_scan.regime_backtest_runs
 WHERE indicator='cri' AND completed_at IS NOT NULL
 ORDER BY created_at DESC
 LIMIT 5;
```

## 3. What this enables

Research questions now cheap to ask:

### 3.1 "How would a candidate v4 calibration change CRI's 20y AUC?"

1. Bump `COMPOSITE_VERSION` in `src/uw_scan/cards/cri_scorers.py` (e.g., 3 → 4) on an experiment branch
2. Change calibration constants in the same module
3. Re-run: `uv run python scripts/backtest_cri.py --note "v4 candidate: VVIX floor 75 / VIX RoC sub-score"`
4. Compare via §2.2 SQL query — see auc_dd5 / auc_dd10 side-by-side
5. The production API surface is untouched: `find_latest_run` filters on the *current* (un-bumped) constant; experimental runs are SQL-only.

### 3.2 "Does VCG fire during regime X?"

```sql
SELECT trade_date, score, level,
       payload->>'vcg' AS vcg, payload->>'vcg_adj' AS vcg_adj
  FROM uw_scan.regime_backtest_daily
 WHERE run_id = (SELECT MAX(id) FROM uw_scan.regime_backtest_runs
                  WHERE indicator='vcg' AND completed_at IS NOT NULL)
   AND trade_date BETWEEN '2020-02-01' AND '2020-04-30'
   AND level IN ('RISK_OFF','EDR','BOUNCE','WATCH','PANIC')
 ORDER BY trade_date;
```

### 3.3 "What does CRI v3 say about every Fed meeting day?"

Maintain a small `fed_meetings(meeting_date)` reference table, then:

```sql
SELECT m.meeting_date, d.score, d.level, d.payload->>'fired' AS fired
  FROM fed_meetings m
  JOIN uw_scan.regime_backtest_daily d
    ON d.trade_date = m.meeting_date
 WHERE d.run_id = (SELECT MAX(id) FROM uw_scan.regime_backtest_runs
                    WHERE indicator='cri' AND completed_at IS NOT NULL);
```

### 3.4 "Where do CRI and VCG agree?"

```sql
SELECT c.trade_date, c.score AS cri_score, c.level AS cri_level,
       v.score AS vcg_score, v.level AS vcg_level
  FROM uw_scan.regime_backtest_daily c
  JOIN uw_scan.regime_backtest_daily v ON c.trade_date = v.trade_date
 WHERE c.run_id = (SELECT MAX(id) FROM uw_scan.regime_backtest_runs WHERE indicator='cri' AND completed_at IS NOT NULL)
   AND v.run_id = (SELECT MAX(id) FROM uw_scan.regime_backtest_runs WHERE indicator='vcg' AND completed_at IS NOT NULL)
   AND c.level IN ('HIGH','CRITICAL')
   AND v.level IN ('EDR','RISK_OFF','PANIC')
 ORDER BY c.trade_date;
```

## 5. Open research questions

From `cri-methodology.md` §7 and surfaced by this closure:

1. **CRI**: VIX term-structure (contango ↔ backwardation flip) as a fifth component — would need 4×25 → 5×20 redistribution; data dependency on VX futures.
2. **CRI**: tactical vs. structural sub-score weighting — currently fixed at 10/15 in v3 (`structural=0–15 vs 100d MA`; `tactical=0–10 vs 20d high`). Are the weights right? Optimisable against the OOS labels.
3. **VCG**: the 52% `SUPPRESSED` rate. Is the 21-day OLS window too short? Should the sign gate be a band rather than strict ≤ 0?
4. **VCG**: HYG vs JNK vs LQD A/B comparison. Run the backtest against all three; compare named-crash window evidence. (Mechanical: three `scripts/backtest_vcg.py --proxy X` invocations + a comparison SQL.)
5. **VCG**: VCG was late on Lehman (BOUNCE day 0, RISK_OFF day +3). Was that a model failure or a real characteristic of the 2008 credit-stress timeline? Compare against COVID 2020-03-16 (also late) and Volmageddon 2018-02-05.
6. **Both**: cross-indicator co-firing — when do CRI HIGH/CRITICAL and VCG EDR/RISK_OFF align? When do they diverge? Diverging days are the most interesting research material (one indicator sees something the other doesn't).

## 6. How to extend (for a future contributor)

### 6.1 Running a calibration experiment

1. Branch from `main`: `git checkout -b feat/cri-v4-experiment`
2. Bump `COMPOSITE_VERSION` in `src/uw_scan/cards/cri_scorers.py` (or `vcg_scoring.py` for VCG) — e.g., 3 → 4
3. Edit calibration constants in the same module
4. `uv run python scripts/backtest_cri.py --note "v4: try VVIX floor 75"`
5. Inspect via §2 SQL cookbook
6. **No** API or UI side-effects: `find_latest_run` filters on the un-bumped constant in `main`. Your candidate run is SQL-only.

### 6.2 Promoting a candidate to production

1. Merge the calibration commit to `main` (changes `COMPOSITE_VERSION`)
2. **Update `LAST_KNOWN_AUC_DD5` / `LAST_KNOWN_AUC_DD10`** in `cri_scorers.py` with the new run's AUC numbers — PR review enforces this contract
3. Update `cri-methodology.md` §3 with the new threshold values
4. Add a new entry to `cri-methodology.md` §3 version history
5. Re-run `scripts/backtest_cri.py` in prod after deploy — the API will now serve the new run

### 6.3 Where the math lives

### 6.4 Version conventions

- `COMPOSITE_VERSION` is an integer in code, serialised to a string in `regime_backtest_runs.composite_version` (TEXT column).
- Production runs use the current code constant. Experimental runs use any string the human chooses (e.g., `"4-candidate"`, `"5a-vvix-floor-75"`). The API only serves rows matching the current production constant.
- The version string is provenance-bound to the code by import at script-run time. Never override on the CLI.
