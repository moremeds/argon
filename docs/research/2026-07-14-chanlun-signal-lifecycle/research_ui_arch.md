## 1. `createSeriesMarkers` capability audit (v5.2.0)

Source: `typings.d.ts` lines 3938–4022, 2634–2648, 4904–4930; renderer internals `lightweight-charts.development.mjs` lines 15522–15852 (`SeriesMarkersRenderer`, `SeriesMarkersPaneView`, `fillSizeAndY`).

**Per-marker fields** (`SeriesMarkerBase<TimeType>`, `typings.d.ts:3947-3984`):
`time`, `position` (`aboveBar|belowBar|inBar|atPriceTop|atPriceBottom|atPriceMiddle`), `shape` (`SeriesMarkerShape = "circle"|"square"|"arrowUp"|"arrowDown"` — 4 shapes only, no hollow/outline variant), `color: string`, optional `id`, `text`, `size` (multiplier on bar-spacing-derived shape height, default 1), `price` (required for the `atPrice*` positions).

**Color / alpha — verified, no restriction to hex.** `drawItem()` (mjs:15601-15607) does `ctx.fillStyle = item._internal_color;` directly, then draws both the text (`drawText`) and the shape with that same `fillStyle` — the string is handed straight to Canvas2D, so any valid CSS color syntax works, including `rgba(r,g,b,a)` and 8-digit hex (`#RRGGBBAA`). This is a real, load-bearing finding: **per-state opacity is achievable purely via the `color` string, no custom primitive required.** One consequence: text and shape are always the same color (single `fillStyle` for both) — you cannot color the glyph differently from the `?`/suffix text.

**No dedicated opacity or z-order field per marker.** `zOrder` (`SeriesMarkersOptions.zOrder`, `typings.d.ts:4001-4022`) is a *plugin-instance*-level option (`"top"|"aboveSeries"|"normal"`), applying to the whole `createSeriesMarkers()` primitive, not per marker. Argon's `TechnicalsPriceChart.tsx` currently creates one `clMarkers` primitive for all Chanlun markers (points + segment points + divergences) — a per-state z-order would need either accepting one shared z-order for all states, or splitting into multiple `createSeriesMarkers` instances (one per lifecycle state), which is more plumbing than it's worth for this feature.

**Two markers CAN share a bar.** Confirmed in `SeriesMarkersPaneView._internal__makeValid()` (mjs:15780-15843): markers are grouped by `time`, and for each new bar the stacking offset counters (`offsets._internal_aboveBar` / `_internal_belowBar`) reset; `fillSizeAndY()` (mjs:15680-15727) increments the offset for each subsequent marker at the same position on the same bar. The library does not merge/dedupe same-bar markers — it renders both and stacks them vertically (e.g. two `aboveBar` markers on the same day render as two glyphs, offset apart). This already matches how the codebase pushes multiple marker sources (`points`, `segPoints`, `divergences`) into one array sorted by time (`TechnicalsPriceChart.tsx:811-833`).

**Custom primitive (like `chanlunZhongshu.ts`) — not needed for fade, needed for hollow.** Because alpha is expressible in the `color` string, "fading" (discrete alpha per bar-age, recomputed on each data pass) needs zero new primitive machinery — just compute a different `color` string per lifecycle state/age when building the marker array. A custom `ISeriesPrimitive` (in the vein of `web/lib/lwc/chanlunZhongshu.ts`, 149 lines: `IPrimitivePaneRenderer` + `IPrimitivePaneView` + attach/detach lifecycle) would only be required if the design wants something the marker shape set can't express — e.g. a **hollow/outline** marker (today's shapes are filled circle/square/arrow only, confirmed in `drawShape()` mjs:15608-15627) or true continuous (per-frame) opacity animation rather than discrete per-bar-age steps. Cost estimate for that primitive, by direct analogy to `chanlunZhongshu.ts`: ~120-160 lines (renderer + pane view + attach lifecycle + a `setMarkers`-equivalent setter), one-time cost, same shape as the existing 中枢 rect primitive.

## 2. Current wiring vs. three states

Marker-building block: `web/components/stock/panels/TechnicalsPriceChart.tsx:799-833`. Today's `marker()` helper (lines 799-809) and the divergence inline map (819-831) both do:
```ts
text: `${prefix}${p.kind}${p.confirmed ? "" : "?"}${p.resonant ? "★" : ""}`,
color: buy ? positive : negative,   // fixed by side, never by lifecycle state
```
i.e. `confirmed: boolean` is the only lifecycle signal that exists today, rendered purely as a `?` text suffix; there is no `invalidated` state at all — an invalidated point just fails to appear in the next `chanlunGeo` memo output (see §3) and vanishes with no visual trace.

**Minimal representation to add a 3rd state**, staying inside the existing shape (no new lightweight-charts feature required):
- Extend `BuySellPoint`/`DivergenceMark` (`web/lib/chanlun.ts:54-69`) — or a wrapper type built in the component — with a tri-state `status: "pending" | "confirmed" | "invalidated"` (derived from `confirmed` today; `invalidated` needs the lifecycle memory discussed in §3) plus, for invalidated marks, an `ageBars` or `expiresAtBarIndex` counter.
- `color`: same base hue as today (`positive`/`negative`/`divColor`), alpha varies by state — e.g. `confirmed` = full alpha (as now, opaque hex/rgb), `pending` = same hue at ~70-80% alpha (visually "still forming"), `invalidated` = same hue fading from ~50% down to ~0% alpha over the 5-10 bar window, then dropped from the array entirely once alpha hits 0 (equivalent to today's "vanish", just delayed and softened).
- `text` suffix convention stays additive: keep `?` for pending (as today), add e.g. a strikethrough-style prefix or a small `✕` glyph for invalidated so it reads distinctly from pending even before the alpha fade registers, since text/shape share one `fillStyle` (see §1) — no independent text color available to signal state.
- **Practical blocker to flag:** `cssVar()` (`TechnicalsPriceChart.tsx:80-85`) resolves Argon's CSS custom properties (`--positive`, `--negative`) via `getComputedStyle(...).getPropertyValue(...)`, and the repo's own hardcoded chart colors are written as plain hex or `rgba(...)` literals (e.g. `chanlunZhongshu.ts:33-34`: `"rgba(120, 160, 255, 0.08)"`). Nothing today guarantees `cssVar()` returns a 6-digit hex you can safely suffix with an alpha byte (`#RRGGBBAA`) — a ~10-line `hexToRgba(hex, alpha)` (or regex-based) helper is needed before per-state alpha can be layered on top of the existing `positive`/`negative`/`divColor` variables. Small, not a blocker, but not automatically free either.

## 3. Where "invalidated" comes from at all

`computeChanlun()` (`web/lib/chanlun.ts:394-468`) is a pure function with **zero memory across calls** — every invocation (memoized on `rows`/`full` in the component, per `web/CLAUDE.md` conventions) recomputes the entire structure from scratch. Verified structurally: the provisional-tail logic (`chanlun.ts:400-435`) is the sole invalidator —
- `confirmedCount = eps.length - 1` before the trailing extension step;
- the loop at 407-419 may overwrite `eps[eps.length-1]` in place with a new, farther extreme (`extSame`) if the running same-direction extreme has moved past the old tail vertex;
- the loop at 422-434 appends a `forming` counter-leg vertex.
- Downstream, `vertices`/`pts` mark `confirmed: i < confirmedCount` (438-450), and `markPoints()` (`chanlun.ts:296-355`) sets a `BuySellPoint.confirmed` directly from its anchor vertex's `confirmed` flag (`mark()` helper, line 303-306: `confirmed: v.confirmed`). This means **at most the last two vertices in `eps` are ever unconfirmed** at any single call — everything before `confirmedCount` is permanently confirmed by construction, and a BSP/divergence is unconfirmed iff it's anchored at one of those last two.

Because a single call only ever returns "the current best guess of the tail," the only way to know a *previous* tail guess existed and got superseded (i.e., to synthesize an "invalidated" event) is to compare two different calls to `computeChanlun` — there is no way to derive it from one call's output alone, no matter how much bookkeeping is added inside the function, unless that bookkeeping *is* effectively a replay (see 3b below).

### (a) Client-side prefix replay, K=60

Call `computeChanlun(bars.slice(0, n-K+i))` for `i = 1..K`, i.e. re-run the full pipeline K times with the bars array truncated at each of the last K positions, then diff consecutive outputs' unconfirmed-point sets by `time` to reconstruct a PENDING→CONFIRMED/INVALIDATED history for the visible tail window.

- **Cost:** `computeChanlun` runs `mergeInclusions`, `findFractals`, and the leg/pivot/BSP pipeline over the *entire* `full` bars array each call (there's no evidence in the code of an early-exit or windowed variant — `eps` is built by walking merged candles from the start, and 笔/中枢 construction chains sequentially from the first fractal), so each call is O(n) over ~1300 daily bars. K=60 replay calls → ~60× the cost of today's single memoized pass, i.e. roughly 78,000 bar-touches instead of ~1,300, on every data pass (which per `web/CLAUDE.md` fires on ticker/window/mode changes and on live-bar appends). This is a real, non-trivial CPU cost on the client — likely needs its own `useMemo` keyed narrowly (e.g. only on `full.length` bucketed, not on every intraday tick) and possibly deferral to an idle callback or a Web Worker to avoid blocking the render/interaction thread. It is *not* free, and the K=60 default is a real tuning knob, not a rounding error.
- **Where the memo lives:** parallel to the existing `chanlunGeo` memo in `TechnicalsPriceChart.tsx` (line ~866's `useMemo` deps list: `[rows, full, ticker, candleMode, anchor, mode, chanlunGeo]`) — a second memo, e.g. `chanlunLifecycle`, keyed on the same `full`/`ticker` but internally short-circuiting (only recompute the replay when `full.length` has grown, and even then only recompute the *new* suffix rather than all K positions from scratch, i.e. an incremental cache of the last K snapshots keyed by bar index).

### (a′) Cheaper variant found during research: pass-to-pass diff (not asked for, but concrete and near-free)

Rather than replaying K historical prefixes, keep a `ref` holding the previous data pass's unconfirmed `{time, kind}` set (BSPs/divergences with `confirmed === false`). On each new pass (already computing `chanlunGeo` once, at today's cost), diff: any previously-unconfirmed `time` missing from the new pass's unconfirmed OR confirmed sets = invalidated *as of this pass*; start its fade-out timer then. This costs effectively zero extra compute (no extra `computeChanlun` calls) but **only detects invalidations that happen while the chart is open in that browser tab** — a fresh page load / ticker switch has no prior-pass history, so it cannot show "this was invalidated 3 bars ago" for history that predates the session. Worth flagging as a possible first cut if the goal is purely "reduce noise while actively watching," deferring true historical replay/persistence to a later stage.

### (b) Single-pass analytical derivation inside `computeChanlun`

Concretely against the code: the tail-extension loops (`chanlun.ts:407-419`, `422-434`) are themselves forward scans over merged candles `m`, and in principle you *could* record, at each `j`, what the tail vertex would have been "as of" that candle — turning the K separate top-level `computeChanlun` calls into one internal forward pass that snapshots `eps` state at each of the last K candle indices. That addresses the *vertex*-level provisional history cheaply (genuinely O(n), not O(K·n)). **But it doesn't fully solve the problem**, because BSPs/divergences aren't a function of the tail vertex alone — `markPoints()`/`markDivergences()` (`chanlun.ts:296-385`) consume `legs`/`pivots` built from the *entire* `eps` array (`buildLegs`, `buildPivots`, `pivotsToZhongshus`), and those are not written as incremental/streaming functions today. To get a true single-pass derivation of "what BSPs existed as of each of the last K bars" you'd need to either (i) re-run `markPoints`/`buildLegs`/`buildPivots` at each snapshot anyway (which collapses back to something close to the O(K·n) cost of full replay, just avoiding the `mergeInclusions`/`findFractals` re-scan), or (ii) rewrite the leg/pivot/BSP pipeline to be genuinely incremental (append-only, update in place as new candles arrive) — a substantial refactor of `chanlun.ts`'s core (`buildLegs`, `buildPivots`, `pivotsToZhongshus`, `markPoints`, `markDivergences`, currently ~250 lines of the 574-line file) with real correctness risk (the file's own comment at `chanlun.ts:9-11` stresses the trailing structures are provisional-by-construction and repaint-prone; an incremental rewrite has to preserve that repaint behavior exactly or silently changes signal semantics). **Verdict: theoretically cheaper, practically a multi-week correctness-sensitive rewrite, not a "small bookkeeping" change** — the task's framing ("small amount of extra bookkeeping") undersells what full incrementalization would cost; the vertex-only partial version is feasible but leaves BSP invalidation unsolved.

### (c) Server-side persistence (Python port)

A Python port of `computeChanlun` (or a subset — just the tail/BSP invalidation logic) running at daily close, persisting `pending`/`confirmed`/`invalidated` rows to Postgres as an append-only event log, with the client rendering event history instead of re-deriving it. This is the only option of the three that gives a durable, cold-load-correct history ("this point was invalidated 3 days ago" is answerable even for a user who just opened the page) rather than a client-session-scoped approximation.

- Aligns directly with the repo's Stage-1 "signal→alert pipeline" deliverable (`CLAUDE.md` mission section: "ship alerts on existing signals... without waiting for a promoted signal") and with the standing rule "Persist analytical results to Postgres — vol/scan/regime outputs land in tables, never in-memory-only" / "If a research/analytical function doesn't already write to the DB, the caller must persist the result before the run counts as done."
- Existing precedent in-repo for exactly this shape of job: `worker/jobs/technical_daily_refresh.py` / `technical_live.py` (daily EOD job + storage repository + API route), and the migration-numbered domain-table pattern (`storage/{domain}.py` + migration) documented in root `CLAUDE.md`'s "Where to look first" table.
- Real cost: a genuine Python port of ~574 lines of TS geometry (`chanlun.ts` + `chanlunSeg.ts`) with parity testing against the frozen AAPL fixture already used for the TS tests (`web/tests/lib/chanlun.test.ts`, per memory `project_chanlun_view.md`) — nontrivial but bounded, and it's work the memory index already flags as deferred ("v2 = 线段/multi-TF/Python port for alerts").

## 4. Recommendation

Ship in two stages, don't try to solve "cold-load correct history" client-side:

1. **Now (small, low-risk):** add the tri-state color/alpha representation (§2) plus the **pass-to-pass diff (§3, option a′)** — near-zero extra compute (no new `computeChanlun` calls, no K-bar replay), reuses the existing `chanlunGeo` memo, and directly satisfies the stated goal ("shown briefly, fading... to limit chart noise") for anyone actively watching the chart. Explicitly scope it as session-local: invalidations that happened before the tab was opened are not backfilled.
2. **Defer full K-bar replay (3a) — don't build it.** Its cost (~60× compute per pass) buys only a client-reconstructed *approximation* of history that a server-side event log gives you for free, durably, and query-able across sessions/devices. It's the worst of both worlds: expensive AND not durable.
3. **Defer the incremental single-pass rewrite (3b)** — real engineering risk against provisional/repaint semantics the code explicitly calls out as fragile; only worth it if a Python port (3c) turns out to need the same incrementalization for its own perf reasons, at which point do it once, in the port, with proper test coverage.
4. **Treat 3(c) — server-side persistence — as the correct destination**, not urgent for the "reduce noise" ask alone but already load-bearing for the repo's Stage-1 alert-pipeline goal; when that work starts, this UI ships against real persisted lifecycle events instead of client-reconstructed ones, and the client-local diff from step 1 becomes redundant (kept only as a same-session fast-path, or removed).
